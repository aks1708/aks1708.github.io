 I'm not on social media anymore so I don't really see everything that's popping. However a friend of mine sent me this X [post](https://x.com/v0xium/status/2101526107128529120) over WhatsApp which she saw on an Instagram post. So I open it and read this rant on how software engineering appears to be dead. How everyone is just vibe coding stuff, almost zero code reviews done by humans and this agenda of shipping software as fast as possible. How large language models have dominated the entire workflow and those days of coding with your own bare hands have disappeared.

 As a software engineer at my previous role, I have seen for myself how generative AI has shaped a new era of software development. We have a relatively new field called AI Engineering, which you can think of as traditional software engineering + AI. The integration of models such as Claude, Gemini and GPT into applications. As well as what we are building, HOW we are building has significantly changed. Back then we had the grind of tying logic together manually, looking up code documentation, Stack Overflow (a forum for coding questions), pulling your hair out until it worked. The satisfaction after all that grunt work is just amazing. At that time, you felt in control of what you were building and you were understanding what was being developed. Headphones in, a cup of coffee (I prefer tea personally) and it's just you, your keyboard and your favourite coding environment. Nowadays why bother when we can simply feed a prompt to an LLM and it goes and cooks for us?

LLMs that were intially designed for text generation have become extremely popular for coding. It's really text generation following a stricter set of rules where we need to use precise keywords depending on the language, respect syntax, indentation and the logic actually needs to flow. We first started with copying and pasting between ChatGPT and our coding environment. Then we progressed to coding agents that have your codebase as context and are able to read and modify these files directly and this is where tools like Cursor and Copilot came into play. Now there are many more such as Anthropic's Claude Code, OpenAI's Codex and open source implementations like OpenCode. LLMs alone are not effective for this use case. It is the scaffolding done around these models that bump up their capabilities. This is what we call a *harness*. All of these cogs working together like memory, tool calling, sandbox execution to run scripts, sub-agents for task delegation. Even something more basic like the system prompt giving the LLM a persona of a software developer. In fact if you see the coding benchmarks [here](https://artificialanalysis.ai/agents/coding-agents), a given score is not just attributed to the model but also the harness used, indicating its importance to the overall performance.

We humans are naturally wired to take the path of least resistance so the rapid adoption of these tools makes sense. Given that these models have progressively become smarter and generally improved in coding across languages, it's basically become the norm for companies to demand their developers use them in the hope they can build and ship products quicker. What I also saw was this shift from specific roles to full stack engineers. We used to have this separation of backend engineers, frontend engineers, Python developers, Android developers etc. I have seen this expectation for people to become more comfortable working with any language. Personally I come from a Python background but in a previous project I needed to use Java, a language I knew nothing about, to patch security bugs and code up a feature. So naturally I had to vibe code it just praying that it worked (which luckily it did) and not break anything else in the process. I do believe this adoption was also down to the fearmongering behaviour that we saw since ChatGPT came out. The message that constantly screamed at us was that if we don't use AI then we would fall behind. That combined with this idea that the best workers are the most productive, it followed that people jumped on this train and made it ubiquitous, including at work. Even then, there was and still is this widespread panic of AI taking over software engineering which I'll come to next.

When I first heard this statement about AI taking over software engineering, I thought it was bullshit. Why? Well what comes to mind when you think of software engineering? The coding right? That's the fun bit. It's like in the machine learning community where we bang on about building a model because that's the most exciting bit but is actually a small part of the broader process. Coding does not fully entail software engineering. It is simply a way to translate logic into something a machine can parse and execute. Where is that logic coming from? Us! Engineering is about taking a business problem and understanding the requirements. What it must do and what's nice to have. Constant communication within the team and whoever the product is for to track progress and brainstorm ideas. Architecting the solution that aligns with these goals and making those design choices. The traditional software development principles still apply. How can it be scalable, secure, reliable, available and something that people actually use? Something that is production ready. What about the evaluation process? Testing your software, demoing, getting feedback, iterating to make it better still in alignment with the core goals. I just don't see how all of that can be replaced by AI. 

How about the way we conduct software engineering interviews? There should be more emphasis on system design and architecting solutions. That is actually something that people would use in their job unlike LeetCode style questions which I just don't think are that effective for finding a top software engineer anymore. These are questions that can be done with no library installations and I think the LLMs are at a point where they can just do it for you. Focus on the things it CAN'T do so well.

That being said, you gotta be careful when working in real software engineering projects. Sure in my case I got lucky and yielded what myself and the team wanted. I had deadlines to meet too so speed mattered. But let's not forget how these GenAI models were trained. They saw data include codebases up to a certain date. As a developer you would know that over time libraries are updated just like we have software updates on our devices. Functions become deprecated, security patches are fixed and more efficient implementations of a specific task. How can you be fully sure the coding agent will be aware of these changes? Well you may think ok we have a harness that can search up the web for the latest documentation right? And yes that would be an ideal situation. But again this is something left to chance unless you explicitly tell it to use the web. You may not care so much when it's a POC (proof of concept) and you could get away with it but when we talk about production grade solutions, this can become quite dangerous. Using an outdated package which opens the door for a major security vulnerability? Yeah I don't think so!

I don't deny that LLMs have value in coding tasks. It's helped me in my previous role and even now it does. I've used it for building the simple layout for my blog with HTML, CSS components and even Ruby's Gemfile. This was a small job so I had enough confidence in the LLM to do this and thus I could shift my focus towards writing these blog posts. That's what this adoption has induced. This shift from doing menial tasks and directing more attention towards the more complex and interesting problems at hand. The problem is when we work with potentially LARGE codebases, shipping code into production and in doing so we blindly trust the code the LLM spits out. Almost zero oversight from humans on whether the code generated follows best practices, is free of security vulnerabilities and just a lack of understanding of what's been built. When it comes to debugging, we just shove it into our coding agent and pray it fixes these errors without breaking something else. This constant tussle with the coding agent resulting in more and more tokens being used up. Let's not forget that! When you consider the scale of adoption, how frequently people are using these models and the duration of these chats with the LLMs (due to complexity), it really can blow the budget. Especially in the enterprise subscriptions where you are paying per million input tokens (what you feed into the model) and per million output tokens (reasoning + final output). You pay regardless of whether you get the result you wanted or not. Uber already exhausted their entire token budget in just 4 months earlier this year sparking doubt in the adoption of these tools.

If we are to make the case that generative AI is great for coding, then rather than simply evaluating whether it works or not by running a script, we need to be more holistic and look at the quality of software being produced. At the moment there seems to be nothing that backs that up mainly due to the fact that AI generated code just poses a higher security risk. Again, to reiterate I am not saying generative AI is useless for coding, I just feel there needs to be a greater responsibility from humans to verify what is being generated and perform rigorous checks before rolling it out. It's one thing to be fast, it's another to produce quality and from what I am seeing, we aren't really there at the moment.
